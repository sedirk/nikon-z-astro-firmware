## 1. 新确认的 `0x29c` 参数控制

原厂函数 `0x10114136` 读取通用配置字节 `0x29c`，对应 RAM `0xc20aaa64`。

- 非零分支直接将输出结构 `+0x62、+0x64、+0x66、+0x68` 的四个半字及上下文 `0xc1884918+0x1c` 清零，然后返回。实验覆盖配置值 0/1；“任何非零”来自指令中的 `CBZ`。
- 零分支计算一个数值，限制到 `[-512, 511]`，以低 10 位形式编码，并按模式与选择字节写入上述某一个槽，其余槽清零。
- 正常分支还更新输出 `+0x60`；非零配置的提前返回不会更新它。其他参数不因此全部清零。
- `0x101145b0` 调用该函数；正常自动计算入口为 `0x1011308c`，另有从配置对象 `+0x110=1、+0x114` 取人工指定输入的原厂分支。

**上述是参数运算事实，不是参数物理含义的证明。** 当前标签为“有符号伴随参数”。“基线补偿”“阈值调整”“暗信号补偿”仅为待区分假设，不将它命名为 BlackLevel 或 True Dark Current。

隔离执行原厂函数：12 个边界／舍入输入 × 6 组模式与选择字节 × 配置 0/1，共 144 组；检查完整输出、未改写区域、尾部保护字节及缓存字段。人工指定分支、配置初始化标志、私有对象地址均在脚本和结果中列出，没有替换函数返回值或模拟像素运算。

首次 9 组后出现断言失败：检查器把正数输入 64 的结果预期成常规四舍五入。原指令在该分支按**截断后的商**决定增减，商为零走减一，实际得到 -1。修正检查器后全部通过；失败结果与当时脚本仍保留。该输入是人工参数，不能据此宣称真实相机存在舍入故障。非零用例目前由 Unicorn 与原指令相互核查，尚未做 QEMU／真机非零交叉验证。

## 2. 从参数到硬件提交已连通

静态反汇编及 32 组原厂代码隔离执行确认：

```text
0x10114136：计算／清零四个参数槽
  → 0x100bed06(0, 参数结构)：打包到 0xc25ee130
  → 0x100d8582(0xc25ee130 + 0x5c)
  → 0x1010b8aa：写硬件寄存器
```

| 原参数半字 | 打包对象偏移 | 最终寄存器位置 |
| --- | --- | --- |
| +0x60 | +0x88 | `0x2006b384`，此项不属于配置提前返回清零的四槽 |
| +0x62 | +0x8a | `0x2006b388[9:0]` |
| +0x64 | +0x8c | `0x2006b388[25:16]` |
| +0x66 | +0x8e | `0x2006b38c[9:0]` |
| +0x68 | +0x94 | `0x2006b390[25:16]` |

中间 `+0x90/+0x92` 被打包函数置零，分别进入 `0x2006b38c` 高位和 `0x2006b390` 低位。寄存器打包器对这些槽取 10 位。

32 组实验使用配置 0/1、四种槽选择及输入 -65536/-128/64/65408，连续执行上述三段未修改的函数。MMIO 地址映射为隔离进程中的普通 RAM，**仅验证写入字节，不实现硅片的像素处理**。

完整 QEMU 跟踪也观察到该驱动的三个寄存器写入。在本次模型零数据条件下值为零；当前 QEMU 对这些配置只存取，不由它们驱动真实的 RAW 校正算法。不能以参数清零或模拟画面不变宣称真机关闭处理成功。

## 3. 与静态拍摄的联系：发现复用路径

第二次跟踪在原厂无卡请求后的静态提交阶段记录到：

```text
0x10076a08：静态帧下层提交
  → 0x10076bc6 / 0x100a2098
  → 0x10114bb2：复用参数并按本次输入更新
  → 0x10114cc4：返回，输出地址 0xc2528b04
  → 0x10076b10 / 0x100bf0fa → 0x100bed06(0, 0xc2528b04)
  → 0x100bf0f4：打包完成
```

`0x10114bb2` 先复制 `0xc1884d70` 中 0xac 字节参数，然后从 `0xc1884918+0x1c` 取缓存值写入 +0x62/+0x64/+0x66，按输入字节选择一槽，其他槽清零。**此路径本身不重新读取 `0x29c`**。因此，不能假定临时改动该配置后，本次静态拍摄立即采用新的偏移；还需要确认原厂重新计算和缓存刷新时机。

本次静态参数的三段地址变成 `0x80660000 / 0x80669720 / 0x80672e40`，对应稀疏列表第 0 组源段；取景参数曾使用第 6 组。这里确认的是**静态参数已选取并打包**，本窗口没有观察到这张静态帧对应的最后寄存器提交，不能写成硬件已消费第 0 组。此前“取景用第 6 组”的事实保留。

第一次跟踪中拍摄 API 调用窗口也出现参数计算，但取景工作可能与请求交错。不能仅凭事件发生在 API 窗口就把它归为静态照片处理；第二次的上面这条带返回地址、输入与输出内存的链条才是静态关联证据。

## 4. 三块表不是新发现的颜色增益表

`0x1011424a` 按模式向输出 `+0x20/+0x24/+0x28` 填入三段地址，基址来自 `0xc1884918+0x3c`。运行时为 `0x80660000`，与数据目录 ID `0x0c` 的地址相同。

将偏移与 ROM `0x11f66eb0` 中既有稀疏列表描述符核对，得到：

| 本函数 mode | 既有列表组 | 三段相对字节偏移 |
| --- | --- | --- |
| 0 | 0 | 0 / 0x9720 / 0x12e40 |
| 1、2、3 | 6 | 0x855c0 / 0x8eca0 / 0x98380 |
| 4 | 2 | 0x354c0 / 0x3d9e0 / 0x45f00 |
| 5 | 4 | 0x5d540 / 0x65a60 / 0x6df80 |
| 6 | 1 | 0x1c560 / 0x24a80 / 0x2cfa0 |
| 7、8 | 3 | 0x4e420 / 0x53480 / 0x584e0 |
| ≥9 | 6 | 0x855c0 / 0x8eca0 / 0x98380 |

30 组隔离执行覆盖 mode 0–9 与三个选择字节；大于 9 的归类来自静态分支。模式数值不是 P/A/S/M，也不直接等于另一个列表消费者的 mode 枚举。没有据此命名 R/G/B，原厂数据类型名仍未恢复。

运行时同一上下文还引用 ID `0x25`（基址 c9958a00，+0x400/+0x800 分别用于其他参数对象）与 ID `0x31`（c996ee3c）。本次只读取各指针起始 0x300 字节，均为零；**不代表完整数据区全部为零，也不代表真机数据为零**。因此零值不能用于判断校正是否在真机生效。
