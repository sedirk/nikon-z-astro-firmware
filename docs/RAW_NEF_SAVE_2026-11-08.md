# 2026-11-08：候选的 NEF 保存端、非零像素往返与样本验收

本轮把 **原厂 NEF 封装、分块写入和独立解码** 接通了。加载全尺寸候选后，原厂代码生成 TIFF/Exif/Nikon MakerNote，选择 RAW 输出缓冲并调用文件写入；12 位和 14 位非零测试文件均由 LibRaw 成功解码，每份 6104×4222 的 25,771,088 个标记码值逐一一致。

这是实际落盘的 **封装测试 NEF**：像素由明确标注的编码后测试数据提供，文件服务由主机适配器承接。传感器、ISP 校正、编码器硬件生产数据及相机存储卡没有用替代算法模拟。全尺寸候选的实际拍摄效果仍由下一轮暗场／平场及边界取样判断；本轮没有把文件往返测试提升为暗电流保留或消圈成果。

当前实验固件仍是 [全尺寸条件候选](RAW_RELEASE_CONTRACT_2026-11-08.md) 中的同一模块和完整 `.bin.lab` 容器，未增加固件修改，也未刷写。用户已说明本机没有 NEF，本轮结束后拍摄原版样本再提供。

## 1. 哪一段已经接通

| 边界 | 本轮证据 | 输入性质 |
| --- | --- | --- |
| 全尺寸候选 → 编码输入 | 复用并执行原厂请求、句柄交换和编码提交前代码；原版选替换缓冲，候选选本阶段输入缓冲 | 私有描述符；硬件提交前停止 |
| 编码结果长度 → NEF RAW 数据块 | 28 组用例、236 段执行，连接原厂长度写回、封装描述符和 chunk 3 | 未压缩模式按跨度×高度计算；压缩结果长度为显式夹具 |
| 编码输出缓冲 → NEF 文件 | 原厂完整头部构造和原厂分块迭代器执行；记录每次实际文件写入的源地址、长度、偏移、SHA-256 | 编码后非零标记；主机文件服务 |
| NEF 文件 → 解码码值 | 独立 TIFF/NEF 读取器和 rawpy 0.28.0 / LibRaw 0.22.2；逐像素核对 | 不调用 postprocess，不去马赛克，不扣黑位 |

两段证据之间仍有一个明确边界：**被候选选中的编码输入，经真实硬件处理后产生什么编码输出**。目前的保存测试在这之后注入标记。因此“原版和候选的封装测试像素相同”只表示同一编码后数据的保存一致，不能据此推断它们拍摄效果相同。

原厂关键路径：

```text
100af648 → 100a323e / 100a3480
  编码输入：frame+1f8 的 RAW 描述符
  编码输出：encoded_handle+58；结果长度：encoded_handle+5c
           ↓
100b1634：package+4 = encoded_handle+50
103269ac → 1026e078 → 1026db48：原厂 NEF 头部构造
  1026ddc4..ddcc：将 RAW 描述符+c 的长度写入 request+2c
           ↓
1027176a → 10271278 / 10271226 → 102710b6
  RAW chunk 3：base = package+4 指向的描述符+8
               length = request+2c；padding = 0
           ↓
1027185c → 103fabac → 主机文件写入适配器
           ↓
独立读取 NEF RAW strip → LibRaw unpack → 全像素比较
```

未压缩后半段 `100a35a2..35a8` 写入 `stride × height`。压缩后半段 `100a3446..344e` 使用结果包 `c23234c8+64` 的长度；零长度使原厂 chunk 选择器返回“跳过”。这些分段测试明确从驱动等待后的 CPU 语句开始，没有伪造驱动完成返回。

证据：`analysis/raw-nef-save-2026-11-08/length-chain/result.json`（本地归档，未公开）、`analysis/raw-nef-save-2026-11-08/encoded-length.txt`（本地归档，未公开）。

## 3. 与暗信号目标直接相关的新结论

**元数据变化和像素变化现在可以用完整文件分开验收。** 仅将四个 BlackLevel 字段由 300 改成 0，原厂头部随之变化，但 RAW strip 和解包后的全部像素完全相同。低于元数据黑位的测试码值也原样保存。此结论覆盖本次编码后数据到文件／unpack 的边界；真实像素在前端或 ISP 内是否已扣减、裁切，另行取样。

12 位与 14 位的黑位数值单位必须对应。LibRaw 对符合其 Nikon 12 位解码条件的黑位除以 4；本轮同一元数据 300 分别读出 75 和 300，与[版本 0.22.2 的处理代码](https://github.com/LibRaw/LibRaw/blob/0.22.2/src/utils/open.cpp#L1107)及 [Nikon 0x003d 解析](https://github.com/LibRaw/LibRaw/blob/0.22.2/src/metadata/nikon.cpp#L563)相符。因此后续不能直接把元数据中的 300 与 12 位像素的 300 当作同一黑位。

本轮主 RAW 的 TIFF Compression 字段是 34713，数据为按行补齐的未压缩位流。不要仅凭这一字段决定实际压缩模式，须同时看 Nikon 元数据、长度和解码路径。本轮解码验证限于此格式；没有用标记数据验收真正的有损／无损硬件编码算法。

四负偏移、`0x720`、两组空间表仍保留原先的定位和独立候选；本轮没有改变它们或实现它们的像素运算。现在可把其结果交给同一套保存／像素审计，而无需继续猜测最终 RAW 文件块来自何处。

## 4. 保留的失败与修正

1. Unicorn 的完整封装尝试进入原厂 RTOS 锁后发生 CPU 异常：保留 header-attempt（`analysis/raw-nef-save-2026-11-08/header-attempt/result.json`，本地归档未公开）。随后转为启动后的 QEMU，锁与元数据服务原生通过。
2. 前两次 QEMU 封装在复制缩略图时读取占位地址 `62933400`，原厂报告 data abort，PC `10170ed4`。补齐独立分配的预览／RAW 空间后继续；未修改原厂指令或跳过异常。
3. 再一次尝试在 `1028ca66` 读取空预览描述符触发异常。该组 13 回调要求描述符，改用明确的空内容描述符；后续原厂封装和写入完整返回。
4. 最早的 6064×4040 全零测试文件能解码，但继承的推荐裁切范围超出此人工几何。后续保留观察对象的 readout=1，原厂尺寸为 6104×4222，推荐裁切位于缓冲内。两者都是夹具，不据此认定真机输出尺寸错误。
5. 首次非零标记按 MSB 位序打包，读出的标记不符；保存字节本身一致。修正测试打包为 LSB 位序后，12／14 位全像素比较通过。错误打包文件与当时源码继续保留在 `qemu-nef-markers/`。

共 9 次 QEMU 会话，其中 3 次上述封装输入失败、6 次生成文件；最终验收计入 4 份正确非零文件。没有重复增加已验证像素计数。

## 5. 下一次直接用真实样本

已增加只读工具 [audit_nef.py](../tools/fw/audit_nef.py)：保存文件／RAW strip／解码像素哈希、位深、黑位、CFA 四位置分布、零值与低于元数据黑位的数量、裁切范围和两文件精确码值差异。平场模式还输出按四个 CFA 位置分开的径向统计；照明和光学暗角仍在其中，不自动把曲线起伏判成固件彩圈。

按 [原版样本拍摄清单](Z6_SAMPLE_CAPTURE_2026-11-08.md)取得偏置、两种曝光暗场和三个亮度平场。先用原版建立黑位、暗信号和空间台阶基线，再与候选真实输出比较。原厂固件版本和拍摄条件随文件一起记录，压缩包中的 NEF 保持相机原始文件。

收到文件后的优先项：

1. 核对实际几何、12／14 位单位、黑位及是否已有零值／低端裁切；原版样本用于诊断基线，不单独判断补丁有效。
2. 对照多曝光平场的 R/G、B/G 空间变化，区分照明／镜头平滑变化与重复的量化台阶，回到既有机身固定标定和后端候选定位。
3. 为候选实际拍摄关联四处数据：前端输入、可选替换输出、编码输入、保存 NEF；尤其检查保留句柄后是否还有原地写入、缓存可见性和释放时序。安装／机身恢复仍是单独的发布要求。
