# 拍摄状态 3：已定位到图像请求的等待与回调

日期：2026-11-02，北京时间。接续[拍摄检查与原厂无卡路径](CAPTURE_GATES_2026-11-02.md)。本轮只使用本地 C3.80 和固定 QEMU `419a1f2`，没有新增网络调研或真机操作。

后续已推进至[图像状态、资源初始化与上游事件](IMAGE_COMPLETION_2026-11-02.md)：本文保留当时的结果；发送候选的条件和更上游通知链见后续记录。

## 本轮结论

原厂无卡请求进入状态 3 的原因已经确认：拍摄序列计数达到请求数量 1，调用 `0x101edf7c(0)` 进入该状态。**这个计数在图像请求入队之后就会更新，不代表曝光或 RAW 处理完成。**

真正尚未解除的下层等待位是 `0x100`。它与一个已提交的图像请求对应：请求实际入队，64 字节参数被完整送到工作函数，工作函数通过启动检查并进入原厂图像控制流程。原厂事件 `0x0415000d` 的消费者负责解除该等待位，但本轮观察窗口内没有收到该通知，登记的回调仍存在。

因此，下一步应追踪图像控制流程为何没有发出该通知，而不再围绕 AF 的 0x24 或快门键位反复尝试。当前没有确认曝光完成、NEF 输出或 RAW 矫正改变。

## 状态 3 的来源和退出路径

三次独立启动均记录了 `c18b84e0+8` 的原厂写入序列：

```text
0 → 1 → 2 → 3
```

状态 1、2 的调用点分别为 `0x101ef08a`、`0x101ef13a`。下层 `0x10200880` 调用 `0x101484ac` 提交图像请求，然后从 `0x10200972` 调用计数更新函数 `0x101ee6c2(1)`。

在计数更新中，服务结构 `+0x34` 为本轮目标 1，`+0x38` 从 0 变为 1。`0x101ee786` 附近比较二者，并检查另一个服务子状态；本轮子状态为 1，于是经 `0x101ee79a` 尾调用 `0x101edf7c(0)`。后者在 `0x101edfa8` 调用状态写入接口 `0x101efbf8(3)`。

API 随后返回 0，但底层序列仍在等待异步工作。不能把 API 返回 0 或计数达到 1 当成“照片已经拍完”。

静态找到的退出链为 `0x102024b6 → 0x101ee7ec → 0x101efe92`。其中还检查 `0x1016ea38()`、服务子状态等条件，最终可经 `0x101efeec` 把状态归零。本轮未在观察窗口命中该清理链，未人为调用它制造归零结果。

## 下层序列具体在等待什么

序列结构位于 `0xc2376050`，本轮最终快照：

| 偏移 | 值 | 有代码依据的解释 |
| --- | --- | --- |
| +0 | 1 | 当前序列类别/有效标记；不擅自命名为某个快门模式 |
| +4 | `0x10200df9` | 状态推进函数指针，含 Thumb 位 |
| +8 | `0x200` | 当前序列阶段 |
| +0xc | `0x102009df` | 当前阶段工作函数，含 Thumb 位 |
| +0x10 | 4 | 工作函数返回的等待状态 |
| +0x14 | `0x100` | 尚未解除的等待位集合 |

动态观察到：图像提交函数返回 0 后，通用执行器在 `0x101fc29a` 把当前阶段 `0x100` 加入等待位，集合从 `0x20` 变为 `0x120`；阶段随后推进至 `0x200`。`0x102009de` 检查未完成位，发现非零则返回 4。

另一路原生通知调用 `0x101fc2a2(context, 1, 0x20, 0x7fffffff)`，清除 `0x20` 后重新运行当前阶段。第二次检查得到 `0x100`，仍返回等待。这是实际运行中的依赖关系，不是仅凭字段名称猜测。

`0x101fc2a2` 是通用的解除依赖并尝试继续执行函数；参数中 r2 是要清除的位，r3 限定继续执行条件。没有在本轮手工调用它或写入等待位。

## 图像请求确实被接收并启动

已连接并观察到的链条：

```text
0x10200880：构造 64 字节图像请求参数
  → 0x101484ac(request, 0x101fe4c1)
  → 0x1013c70e：排队
  → 0x10144b1e：工作函数
      在回调槽 0x0d 登记 0x101fe4c1
      复制请求参数到 0xc236f5e0
  → 0x101413ee(0x80, 0)：启动检查
  → 0x10141374
  → 0x1013f546：后续图像控制调用
```

第三次实验完整比较了提交的 64 字节参数与工作消息 `+8..+71`，逐字节一致。这里是控制参数，**不是 64 字节 RAW 像素，也不是完整 RAW 缓冲**。

启动检查的结果在 `0x10141406` 读到 1，随后命中 `0x10141374` 和 `0x1013f546`。因此已排除“图像请求根本没有入队”“工作函数没执行”和“卡在这一次启动检查”这三个具体假设。

原厂图像控制回调 `0x101430d4` 继续收到事件，包括 `0x04190008`、`0x0419000b`、`0x04180041`、`0x041a0040` 等；这些数字的完整业务名称尚未确认，不据此宣称传感器曝光或静态 RAW 运算已经完成。

## 解除等待的通知已经定位

静态恢复的通知路径：

```text
0x0415000d → 0x101fe4c0
  → 0x101fe5bc → 0x101fe774
  → 排队 1 字节通知给 0x101fdb1a
  → 当前序列标记为 1 时，选择清除位 0x100
  → 0x101fc2a2：解除依赖并尝试继续
```

`0x101fdb1a` 还含对特定输入值/模式的错误处理，所以仅收到该通知也不自动等于图像成功。它负责通知后的序列推进，这一点由指令中的参数装配直接支持。

图像事件通过 `0x1006e360` 把通知号与 `0x04150000` 合并。`0x1006e338` 登记回调，`0x1006e340` 取出并清空登记项。第三次实验结束时，回调槽 `0xc2375ba8`（基表 `0xc2375b74 + 0x0d×4`）仍是 `0x101fe4c1`。

在 `0x1013fd52..0x1013fd64` 和 `0x101433b8..0x101433c8` 附近已找到两个通知号为 0x0d 的静态发送候选。下一轮从其上游条件追踪；目前尚未把两者分别定名为正常完成、失败完成或某个具体硬件中断。
