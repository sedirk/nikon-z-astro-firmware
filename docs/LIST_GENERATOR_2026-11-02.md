# 原厂列表生成器：坐标、相邻点与双模拟器验证

日期：2026-11-02，北京时间。接续 [列表路径追踪](LIST_PATH_2026-11-02.md)。本轮基于本地 C3.80 主程序和固定 QEMU `419a1f2`，无新增网页调研，无固件代码修改，无真机操作。

## 进展与判断

**已实际执行生成 ID 0x0c 数据的原厂函数 `0x10250e28`，恢复了部分输入布局、二维索引转换和编码规则。** 四组人工输入在 Unicorn 与 QEMU 中生成的完整 917,496 字节输出 SHA-256 一致；没有拦截函数返回值或替换原厂算法。

现在有证据将这条路径描述为“按位置筛选、分组并编码的稀疏列表”。输入位置会被拆成两个坐标，相隔两个位置的点会组合成不同编码，附加数值也会进入编码。坏点或特殊像素位置处理是更强的候选，但**尚未证实原厂名称、真实硬件对各编码的含义，以及与暗电流/彩圈的关系**。这里没有对 RAW 像素做图像质量验收。

特别注意：本轮第二坐标的有效边界来自原厂表，例如第 0 组为 `[0,104)`。这不是 Z6 整幅照片的高度；输入索引到真实感光单元、分块或读出通道的映射仍未知。也未把三路输入命名为 R/G/B。

## 数据来源链条

静态确认的上层链条：

```text
0x10148f96
  获取数据目录 ID 0x31、0x0c、0x26
  从 ID 0x31 的 +0x80、+0x13f80、+0x4fc80 取三类源数据
  用 ID 0x26 +0x14 提供参数表
  分配 0xbf400 字节临时空间
  0x10250e28：生成 ID 0x0c 的内容
  0x1014731c(0x0c, …)：提交数据更新
  0x100771be → 0x100bfafe → 0x100bc118：重新构造硬件列表
```

另一个入口 `0x101490e0` 也使用相同生成器。以上调用关系来自指令与原生参数装配；本轮动态执行的是生成器本身，没有在完整启动中观察到这些上层更新入口自行运行。ID 0x31 的内容如何由真机产生、保存，仍未解决。

生成器参数结构：

| 偏移 | 本轮确认的行为 |
| --- | --- |
| +0x00 | 源 A 指针；分三段，每段有数量及 32 位位置索引，首段最大数量 0x1a90 |
| +0x04 | 源 B 指针；每项 8 字节，含位置索引、16 位附加值；首段最大数量 0x1a90 |
| +0x08 | 源 C 指针；32 位位置索引会拼接到源 A 的临时列表，首段最多 0xaa0 项；本轮人工输入中保持为空 |
| +0x0c | 输出地址，对应上层 ID 0x0c |
| +0x10 | 每组 16 字节的参数；本轮人工设为 `[0,0,0,6064]`，不是相机实测参数 |
| +0x14 | 临时工作区，至少 0xbf400 字节 |
| +0x18 | 类型字节；上层此调用设为 2，本轮保持相同值，物理含义未定 |

为了避免调用宿主系统服务，Unicorn 中使用独立内存与原厂启动复制段。QEMU 中通过原厂分配器 `0x1012934a(0,0x47,0x300000)` 分配临时堆内存，通过原厂地址转换函数得到可访问地址。调用结束后原厂释放函数返回 1，整个会话随后关闭。

## 已恢复的算法行为

`0x10250642` 对位置索引 `p` 使用：

```text
y = p / 6064（整数商）
x = p % 6064
```

接着调用模式相关的横向变换 `0x102505c8`，减去参数偏移，调用 `0x1026189c` 检查半开区间范围。构造的中间记录每项 12 字节，含变换后 x、y、附加值和类别字节。后续排序、同位置合并及相邻位置处理位于 `0x102504f0`、`0x10250242` 及相邻辅助函数。

本轮在第 0 组、第 0 路观察到以下结果。坐标均为实验用编码坐标。

| 输入 | 原厂输出 |
| --- | --- |
| 空列表 | 无非零位置编码；每路存在行结束标记 |
| 简单位置 `(100,32)` | 第 32 行出现 `0xa0190000` |
| 简单位置 `(100,33)` | 相同编码移到第 33 行 |
| 简单位置 `(100,32)` 和 `(102,32)` | 组合为 `0xe0190000`；不是两个独立单点编码 |
| `(100,32)`，附加值 512 | `0x00192000`，对应此分支 `(100 << 14) | (512 << 4)` |
| 简单位置 `(100,104)` | 被筛除，完整输出与空列表一致 |
| `(100,32)`，附加值 `0xfffe` | 被跳过，完整输出与空列表一致 |

所有组会按自己的范围处理。第 4 组的例子中 x=100 变成 x=32，单点编码为 `0xa0080000`。不能将该变换直接解释为某种照片分辨率或 Bayer 通道，仍需确认模式枚举。

`0x102516b2` 将中间记录转换为 32 位编码。不同类别分支分别设置高位类别码；部分分支编码 x 与附加值，部分只编码 x。低层硬件实际怎样修复、替换或运算像素没有模拟。生成器还在输出 `+0xd767c` 写入 ASCII `ENDM`；这是格式标记线索，不能单凭名称推断“defect map”。

## 双模拟器结果

原厂生成器在 Unicorn 中完整返回成功，共执行 7 组用例；输出区及工作区之后的保护字节保持不变。空输入、单点、双点、带附加值四组又在完整 QEMU 菜单会话中重复执行，完整输出哈希与 Unicorn 一致。

| 用例 | 完整输出 SHA-256 |
| --- | --- |
| 空输入 | `2cf06bc59f64bbeb81a77dc392b5fa6930f14d84141d98848d367d0695150e49` |
| 单点 | `0f2c20f2d22eceeb1b67930e3a8ee4f1965891bfa3cf9d7f7950b5a0c51810ea` |
| 双点 | `01e80d98504f69a0e7b73e9ca24e5e602fb213af5766cebaba67f5f06c0b2e00` |
| 带附加值 | `50f5d018dbee85d7564d079ed5a5179f7405271acac4f8179ab0487bba973652` |

工作区、输出区、几何参数和输入记录均为显式实验设置。比较包含人工预填的未改写尾部区域；哈希一致说明两种执行环境在相同设置下得到相同字节，不是对真实标定数据正确性的验证。未启用已知会干扰当前 Unicorn IT 指令清零尾部的内存写回调。

## 静态拍照验证推进到哪里

另开完整取景会话，使用上游已有的 `capture_probe` 提交半按、全按、释放全按、释放半按四步输入。没有伪造曝光完成、传感器数据就绪或文件保存。

- 观察器读到请求结构 `+0x08=0`、`+0x0c=3`、`+0x0d=0`，所选列表组为 6。
- 快门输入观察窗口内共 24 个列表相关事件，包含 5 次组选择/硬件指针提交，仍使用第 6 组。
- 未命中列表生成器入口，没有确认完成静态曝光或生成 NEF。上游诊断字段 `exposure_completed` 仍为 null。
- 前后都存在 `active_inhibit_ids=[0x24]`、`release_inhibit_submask=0xc`，应用 stage 为 0。这里将其记录为静态拍摄推进的阻点线索，尚未证明唯一原因或确切来源，也没有强行清除它。

**同日后续更正：** [拍摄检查逆向](CAPTURE_GATES_2026-11-02.md)确认上述 0x24 虽然置位，但已被当前参与掩码排除；`submask=0xc` 正是使其不参与判断的条件之一。不能继续把该项视为实际阻点。原始观察值保留，解释以新证据为准。后续原厂无卡请求已被接受，但曝光完成仍未确认。

独立执行组选择分支 `0x100bc468–0x100bc4a6` 的 112 组人工参数，确认 mode=3 恒选第 6 组，mode=0/1 等选第 0 组，其他值还受 submode 影响。这里的 mode 是请求结构字节，**不是 P/A/S/M 曝光模式名称**。`request+8 != 0` 走另一路，未包含在这个枚举中。

所以，上一轮“取景未使用第 0 组”的发现仍成立，但不能进一步断言空列表开关对所有静态拍摄模式都无效；需要实际打通静态照片路径后确认。
