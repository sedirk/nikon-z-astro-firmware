# 列表来源、硬件提交与模拟器能力边界

日期：2026-11-02，北京时间。接续 [重启后运行记录](POST_REBOOT_2026-11-02.md)。本轮使用本地 C3.80 主程序和固定 QEMU 源码 `419a1f2a91a1f2d3a0209027c29606475f7fe26f`，没有查询新的网络更新，没有修改固件代码或刷写相机。

## 本轮结论

已把 `0x29e` 相关列表追到“数据目录 → 列表重排 → 按模式选择 → 硬件寄存器”的链条。另一条 `0xc18fa970` 路径也已确认使用数据指针，并非简单布尔开关。两者的物理处理意义仍未确定，不能命名为暗电流、黑电平、坏点或彩圈总开关。

最需要保留的新事实：**当前取景模型选中第 6 组列表，但开关为 1 时只有第 0 组被构造成带终止标记的空列表。QEMU 只记录相关配置，没有用该列表计算像素。** 上一轮观察到的 456 个终止标记本身成立，但不能外推为当前硬件消费者已使用这份空列表，更不能据取景成功推断真机关闭矫正成功。

## 1. 列表源地址来自数据目录

固件目录基址 `0xc1880c78`，每项 28 字节。`0x10091d94(id)` 定位目录项；`0x101f624a → 0x101b0856` 在调用相应初始化/就绪逻辑后返回目录项 `+8` 的数据地址。

| 项目 | ID 0x0b | ID 0x0c |
| --- | --- | --- |
| 目录项地址 | `0xc1880dac` | `0xc1880dc8` |
| 初始化后数据地址 | `0x80400000` | `0x80660000` |
| 目录项 +0x0c 的值 | `0x25fff8` | `0x0dfff8` |
| 已确认用途 | 交给 `0x10122852`，存入 `0xc18fa970` | 交给 `0x100bfafe`，存入 `0xc18d20b0`，随后进入列表构造器 |

`0x10091b52–0x10091b5a` 明确将 `0x80400000` 和该地址加 `0x260000` 写入这两个目录项，上一轮的地址相邻假设得到静态证实。这里使用 ID 和偏移作为标签；尚未恢复原厂数据类型名，`+0x0c` 暂按长度字段线索记录。

运行时在 StartLV 诊断调用内捕捉到：

```text
0x10077164 / 0x10077168：获取 ID 0x0c，返回 0x80660000
0x100bfafe：接收源地址，R1=0，登记后通知工作线程
0x100bc118：工作线程开始构造列表，R0=0x80660000
```

当时读取源地址的 `0x0dfff8`（917,496）字节**全部为零**，SHA-256 `bbfba02e21846f1e4dd67048877f7c904c8482ec1ab771a01a3c8e3023c223b1`。这份模型输入缺少真实数据内容；该观察不能说明真实相机相同区域为零，也没有查明真机数据从哪种存储器加载。

## 2. 构造器和硬件消费者已连通

`0x100bc118` 的输出空间长 `0x18f000`，分为 7 组，每组 `0x39000` 字节。实际分配得到的地址有 CPU 可访问地址与供后续使用的另一地址表示，本轮分别观察到 `0x34bc8400` 和 `0x8d2c8400`；固件通过 `0x101e5be2` 及地址转换目录转换，不可直接混用两种地址。

| 配置 0x29e | 固件原生行为 |
| --- | --- |
| 不是 1，本轮以 0 验证 | 清零全部 7 组，按 7 个描述项从源数据重排 32 位条目；每个小列表遇 `0xffffffff` 结束，输出每行最多 128 个 32 位字 |
| 等于 1 | 只清零第 0 组，并在其每 512 字节开头写 `0xffffffff`，共 456 个；第 1–6 组不在该分支的写入范围 |

本轮用明确标记为人工数据的输入验证了正常分支：每组 3 路、每路 104 个小列表，普通描述项按每 8 行交错重排，另一种描述项按 `0x13000` 字节间隔排放。全部 7 组共 2,184 个非空人工小列表逐字节符合独立计算的预期。这个实验说明打包规则，不说明条目是像素坐标、增益系数或其他硬件指令。

在 flag=1 实验前，输出区预填 `0x5a`。执行后第 1–6 组仍保持 `0x5a`，说明它们是**未被重写**，不是由该分支主动清零。两种分支的输出尾部保护字节均未改变。

完整 QEMU 会话补充读取全部 7 组，得到第 0 组 456 个终止标记，其余组全零。随后捕捉到：

```text
0x100bc4a6：组索引为 6
0x100bc4b8：选择 0x8d2c8400 + 6 × 0x39000 = 0x8d41e400
0x100bc5d6：将所选地址放入参数结构 +0x18
0x100bc5f6 → 0x100d85a0 → 0x1010b9d6
0x1010b9fe：执行 STR，将 0x8d41e400 写往 0x2006b3e0
0x1010ba02：写入后继续执行
```

本轮有限观察窗口内，组选择和硬件写入各捕捉到 7 次，均为上述值。所选地址前 128 字节全零。观察器在写指令前后停下记录寄存器，没有读取可能带副作用的硬件状态寄存器。

**这条路径写了列表地址，不能据此声称禁用了整个处理模块。** 真实硬件如何解释列表、空列表及全零列表，还没有独立证据。

## 3. 另一个“缺省校准”调用影响什么

上游控制器将 `0x10122852(0)` 命名为“使用缺省校准分支”。固件本身做的是把 `0xc18fa970` 从 ID 0x0b 的数据地址 `0x80400000` 改成 0。

已找到并核查两个读取路径：

1. `0x1011d55e(mode)`：指针为零则返回 0；非零且 mode 在 0–12 时，按分组返回 `base + 0x1f8000 + group × 0xd0`。mode 分组为 `[0,0,0,0,0,1,2,3,4,2,5,5,0]`，其他值返回 0。用原生指令验证了两种指针值各 14 个 mode，共 28 项；完整取景会话捕捉到 7 次零指针回退。
2. `0x1011c2a0`：若走到对应路径，会按模式选取 ID 0x0b 内部不同偏移的数据与长度，经 `0x101229b8 → 0x10110cba → 0x100cda34` 写入寄存器 `0x20061264`（地址）和 `0x20061268`（长度）。本轮未在有限运行窗口命中这条上传路径；这是静态链条，不能写成已运行验证。

第二条的硬件区域在上游 QEMU 源码中被归入 SDES 配置。该源码命名可作为搜索线索，尚不能替代真机硬件文档。两条路径还会读取独立的 `state +0x14` 数据指针；清空 `+0x1c` 并不等于停用全部相关数据。

## 4. 为什么目前不能用模拟器画面验收关闭矫正

固定版本 `qemu/nikon-z6.c` 对 `0x2006b310–0x2006b3fc` 的写操作保存到 `capture_filter2_config`。全文件中，该数组只有声明及这处存取，没有由它驱动的像素运算。取景合成 ISP 并没有实现本轮追踪到的列表处理。

因此模型画面可以用于确认原厂控制流、参数和寄存器写入，但改变该表后画面不变不能说明真机处理相同。清零 `0xc18fa970` 也只是绕过缺失数据的部分路径；尚未证明它对真实传感器曝光、读出或图像质量的影响。

当前缺少静态 NEF 保存链路和真实数据内容。暗电流保留、黑电平裁切、热像素过滤、空间颜色矫正仍需分别定位，不能将本轮两条路径合并为一个“RAW 无处理”补丁。
