# 图像等待的上游事件与资源初始化

本轮开始于 2026-11-02，整理和校验完成于 2026-11-03 凌晨，北京时间；文件名保留本轮起始日期。接续[拍摄状态与图像请求等待](CAPTURE_STATE_2026-11-02.md)。本轮使用本地初代 Z6 C3.80 和固定 QEMU `419a1f2`，没有新增网络调研。

后续更长窗口已实际观察到完整通知链并清除等待位 0x100，见[11 月 3 日接续记录](SOURCE_TRIGGER_2026-11-03.md)。本文保留当时较短观察窗口的结果，不能据此认定这条通知永远缺失。

## 结论

原厂无卡请求已经走到帧对象分配和资源初始化：图像控制字段从 0 变为 4，工作函数执行，生成帧对象，初始化函数运行到末尾，七个资源字段变为非零指针。**这些是控制流程和对象初始化证据，不是曝光完成、像素有效或 RAW 矫正关闭的证据。**

此前缺失的 `0x0415000d` 通知已经静态连接到更上游：

```text
上游工作函数处理标志 0x2
  → 0x101e2012：收尾函数候选
  → 发出 0x041f0004，带状态字节
  → 0x100714ba：转为 0x0419000d
  → 0x101430d4：图像控制回调
  → 条件满足时发出 0x0415000d
  → 上一轮定位的消费者解除等待位 0x100
```

本轮读取的实际回调指针与这条连接一致，但**没有观察到事件链完整运行**。最终仍为拍摄服务状态 3、图像控制状态 4、下层等待位 `0x100`。下一步可以针对上游标志的产生者和调度条件继续定位，而不必盲目改快门输入或直接清除等待位。

## 图像状态 4 的来源

这里的“图像控制状态”是 `0xc18b7cc0+0x1a`，与拍摄服务 `0xc18b84e0+8` 的状态 3 是两个不同字段。

`0x1013e18a(event)` 经 `0x1006e52e` 查表：

```text
新状态 = ROM[0x114d4678 + 旧状态 × 14 + event]
```

表值 `0x0a` 表示不写入。动态记录到调用点 LR=`0x101413d9`、event=0，旧状态 0 查得 4，在 `0x1013e1a6` 写入。随后 `0x10143c12` 排队，工作函数 `0x1013fcb6` 实际执行。

工作函数的 TBB 跳转表根据状态 0..4 分别跳到：

| 状态 | 目标 |
| --- | --- |
| 0 | `0x1013fd68` |
| 1 | `0x1013fdc0` |
| 2 | `0x1013fd68` |
| 3 | `0x1013fdc0` |
| 4 | `0x1013fce4` |

本轮请求 `0xc236f5e0+8` 为 0，跳过只针对值 `0x0d` 的资源检查分支，进入 `0x1013fd6c`。`0x1013f4fa` 返回 0，因而继续分配对象。没有把状态 4 擅自命名为“曝光中”或“处理完成”。

## 帧对象及资源初始化已实际执行

第三次诊断 lower-probe 观察到：

```text
0x1013fd94 → 0x100769d0
  → 0x1013fa88：分配并准备帧对象
  → 0x10076d0c → 0x100bf354 → 0x100c0362
  → 0x100c0416：资源初始化末尾
  → 返回至 0x10076d14，r0=1
```

`0x1013fa88` 内向分配接口请求大小 `0x1280`。本次帧指针为 `0xc2cc5e48`，记录在图像服务 `+0x24`；帧的 `+0x3a4` 指向配置 `0xc3b53c90`。这里只保存了帧前 `0x400` 字节和配置前 `0xb0` 字节，不是整个对象的完整解析。

初始化后的字段：

| 帧内偏移 | 本次指针 |
| --- | --- |
| +0x1f8 | `0xc2bfed58` |
| +0x220 | `0xc2bf3a48` |
| +0x248 | `0xc2bf3a70` |
| +0x270 | `0xc2bdebf0` |
| +0x298 | `0xc2c41ff8` |
| +0x2c0 | `0xc2c3d4c8` |
| +0x2e8 | `0xc2ca27b8` |

静态代码把一系列资源函数的结果写入这些字段。动态确认第一个写入结果和初始化末尾均被执行，最终七项非零。还没有逐项检查它们的对象内容、大小、像素来源或完整生命周期，因此不能称为“七个有效 RAW 缓冲”。

`0x100c0362` 返回的 1 随后由 `0x10076d0c` 包装为 0；这是局部函数的返回约定，不是拍照成功码。两次完整诊断的堆地址不同，按每次实际指针关联，不把地址固定为永久位置。

## 完成通知的连接与分支条件

### 图像层接收 `0x0419000d`

`0x101430d4` 把输入事件减去 `0x0419000b`，经 `0x101431a4` 的 TBB 表选择分支。事件 `0x0419000d` 的索引为 2，目标确实是 `0x10143398`。

这个分支检查 `0xc18b7dc0+0x4c`：

- 为 0：读取输入状态字节，经 `0x1006e36c` 转换；调用 `0x1013e18a(1)`；取出并清空回调槽 0x0d，发送 `0x0415000d`。
- 非零：转去排队执行 `0x1014300c`，不能直接套用上述分支。

两次完整诊断最终 `+0x4c` 都为 0，回调槽 `0xc2375ba8` 仍登记 `0x101fe4c1`。状态表中状态 4 收到 event=1 会变成 5，但本轮未观察到该转换。

上一轮的另一个发送候选 `0x1013fd52` 已确认位于请求字段为 `0x0d`、资源条件未满足的分支，构造状态字节 2，并调用图像状态事件 3。它不是一个可以无条件调用的“拍照成功出口”。旧日志的 `image_notify_d_normal` / `alternate` 是早期观察点标签，不代表已经确认的正常/异常语义。

### 下层如何发出 `0x0419000d`

`0x100714ba` 接收 `0x041f0004` 时，直接经 `0x100715e2` 跳到 `0x100719fe`。它将输入的首字节转换为 0/1，然后从 `0xc18d1db0+0x44` 取回调，发送 `0x0419000d`。

lower-probe 的最终快照确认：该回调槽是 **`0x101430d5`**，即含 Thumb 位的图像控制回调。这样就把两个模块间的连接从静态候选推进到了实际登记指针验证。

还发现 `0x100721d8` 通过 `0x04190008+5` 构造同一个事件编号，但它使用 **`+0x48` 回调槽**，本次值为 `0x101474af`，并传入空 payload。这与 `+0x44` 路径不同，不能混为一谈，也不能把空 payload 直接送给会读首字节的图像回调。

该次观察到 `0x10072172` 处理的是另一个对象 `0xc2cc5bb0`，首字段 `0xa2`，并非上面的帧对象；其局部检查返回 0，未走到这个第二发送位置。这个对象的完整业务身份尚未确认，不能将其局部返回当成目标照片的失败原因。

### 更上游的 `0x041f0004`

静态发送点为 `0x101e20c8..0x101e20ca`，属于 `0x101e2012`。它从 `0xc18b7228+0x24` 取回调。lower-probe 实际读到 **`0x100714bb`**，与上述接收函数吻合。

工作函数 `0x101e26f0` 将输入标志保存到 r4，在 `0x101e2798` 左移 30 位并测试符号位，即检查原始 **bit 1 / 掩码 0x2**；满足时在 `0x101e279c` 调用 `0x101e2012`。注册代码 `0x101e2b90..0x101e2ba2` 将该工作函数关联到对象 `0xc236d250`。

另在 `0x101e4126..0x101e412c`、`0x101e4142..0x101e4146` 找到对该对象发送 0x2 的候选路径。其所有前置条件和与实际硬件事件的对应关系尚未恢复；这一段只有静态证据。本轮没有命中 `0x101e2012`、发送点或两层接收点，不能据此断言“已经确定缺哪个中断”。

第一次在高频图像回调启用重复断点后，`call_fixture` 预期回到 `0x100202b4`，实际停在 `0x101430d8` 并触发断言，当时 r0=`0x041a0040`。疑似多核单步/重装断点竞争，**根因未证明**；不将其计作通过，也不据此认定固件自身崩溃。后来把该高频回调改为每个诊断调用只观察一次，两个后续诊断正常结束。该变化不构成根因证明。

两次完整诊断均在原厂等待函数输入 100 和 1000 后取快照；最终状态相同。较早快照等待位为 `0x120`，最终为 `0x100`，与此前原生清除 `0x20` 的机制一致。单个诊断调用 trace 最多分别为 42、44 条，低于 256 上限。断点改变运行时序，未命中只表示这些观察窗口内未出现；单次回调观察也不是完整事件总账。

诊断仍沿用上游人工传感器、TG、ISP、RAM 等辅助启动环境，详见前轮记录。没有修改固件代码或 QEMU 设备模型，没有注入完成通知或直接清除等待位，没有连接相机。
