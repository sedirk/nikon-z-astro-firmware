# 专题报告 03：菜单无感切换设计与色空间属性架构深度复盘

## 1. 为什么此前「移到色空间」一直未成功？(The PID 0x0508 Misconception)

在 `Modified16` 之前，天文直通开关曾尝试做在「NEF(RAW)记录 -> NEF(RAW)压缩」菜单中（复用有损压缩选项）。但这带来了一个严重痛点：**开启直通后无法自由选择无损压缩或未压缩 RAW**。

因此自 `Modified18` 起，项目决定将开关迁移至「照片拍摄菜单 -> 色空间（Color space）」（选项 0=标准 sRGB，选项 1=天文直通）。然而用户反馈实刷 `Modified18 ~ Modified21` 之后，实机从未成功开启过直通。

### 1.1 核心根因：属性 ID 误判
通过对 C3.80 原厂固件属性映射表（`0x10070474 / 0x10070478`）和拍摄菜单句柄的深度反汇编发现：

1. **`PID 0x0508` (`RAM 0xC24CDE28`) 根本不是色空间，而是「自动 ISO 感光度控制」**：
   - 菜单句柄 `0x1049B06E`（`String ID 0x01C0`）证实 `PID 0x0508` 属于 ISO 设定子菜单；
   - `0x1040AD00` 是当自动 ISO 处于关闭态（`0x0508 == 0`）时，灰置子选项的条件桩；
   - `0x1014F638` 计算的是照片模式有效自动 ISO 状态（`PID 0x1381`）。
2. **`Modified18 ~ Modified20` 的连带失误**：
   - 门控逻辑误读了 `0xC24CDDC4`（实为 `PID 0x0440` 焦距变化拍摄张数，默认值为 `100 != 1`），导致门控在实拍时恒定返回 0；
3. **`Modified21` 的连锁破坏**：
   - 将门控改为读取 `0xC24CDE28` (`PID 0x0508`) 并将 `0x1014F678` 锁定为 0；
   - 当用户在手动 M 档并关闭自动 ISO 时（`0x0508 == 0`），门控恒返回 0，直通完全不触发；同时还意外把照片模式的自动 ISO 控制给锁死了！

## 2. 真正的「色空间」双层属性架构

C3.80 原厂固件中，色空间体系是由**用户设定属性**与**底层有效状态**解耦的双层结构构成的：

```
用户在菜单中操作 (PID 0x0526)
        │
        ▼  (0x104A149C=0 / 0x104A14A6=1)
[ 菜单属性 PID 0x0526 (RAM 0xC24CDEA0) ] ─── 负责 UI 菜单、i 快捷栏、NVRAM、U1~U3
        │
        ▼
[ 全固件唯一评估器 (0x1014BAEA) ]
        │  原厂代码在 0x1014BB28 处强判视频模式清零
        ▼
[ 底层有效色空间 PID 0x130A (RAM 0xC24CC74C) ]
        │
        ├─► DCF 文件名构造器 (0x10255850): 0 -> "Z61_xxxx.NEF", 1 -> "_Z61xxxx.NEF"
        ├─► MakerNote EXIF Tag 0x001E: 1 -> sRGB, 2 -> Adobe RGB
        └─► Companion/Embedded JPEG 编码管线
```

- **菜单属性 `PID 0x0526`**：
  位于 `RAM 0xC24CDEA0`，Photo Shooting Menu 行 `0x113F0720`（`String ID 0x03B3`）直接调用 `0x10497CD0: movw r0, #0x0526`。`U1/U2/U3` 独立六组存储槽（`0x11F549A4`）也是对 `PID 0x0526` 进行读写；
- **底层有效色空间 `PID 0x130A`**：
  位于 `RAM 0xC24CC74C`，全固件仅由 `0x1014BAEA` 单向计算。相机拍摄时，采集中断句柄 `0x101703DC` 从此处读取值写入 `capture_owner + 0x25D`，直接决定是否在文件名前加下划线（`_Z61`），以及 JPEG 直出与 EXIF 的色域色彩。

## 3. Modified22 的三项彻底修复方案

在 [z6_astro_ui_color_space_v2.py](../tools/fw/z6_astro_ui_color_space_v2.py) 中，`Modified22` 采用了完美的架构收口：

### 3.1 纠正门控谓词 (`0x1002D900`)
```arm
// fn_is_astro_r0:
movw  r1, #0xDEA0
movt  r1, #0xC24C
ldr   r0, [r1]           // 读取 PID 0x0526
cmp   r0, #1             // 是否为直通RAW (1)
bne   .not_astro
movw  r1, #0xC798
movt  r1, #0xC24C
ldr   r0, [r1]           // 读取 PID 0x131B (有效 RAW 记录模式)
cmp   r0, #1             // 必须 <= 1 (0=RAW+JPEG, 1=RAW单摄)
bls   .is_astro
```

### 3.2 锁定有效色空间为标准 sRGB (`0x1014BB28`)
原厂在 `0x1014BAEA` 中存在一段条件分支：
```arm
0x1014BB28: 01 d1        bne  #0x1014bb2e    ; 若满足条件则跳过清零
0x1014BB2A: 00 20        movs r0, #0         ; 否则强行赋 0 (sRGB)
0x1014BB2C: 01 90        str  r0, [sp, #4]
```
我们将其修改为：
```arm
0x1014BB28: 00 bf        nop                 ; 消除条件跳转，恒定执行清零
```
**实现效果**：
- 无论菜单选择「标准」还是「直通RAW」，底层有效色空间 `PID 0x130A` 恒等于 `0 (sRGB)`；
- 文件名恒定为 **`Z61_xxxx.NEF` / `DSC_xxxx.NEF`**，彻底根除讨厌的 `_Z61` 前缀；
- MakerNote `0x001E`、内嵌预览图与 RAW+JPEG 直出 JPG 均保持标准原生的 sRGB；
- 菜单显示、`i` 快捷栏文字、`U1~U3` 状态与 NVRAM 关机记忆均完整保持对 `PID 0x0526` 的记忆。

### 3.3 恢复原厂自动 ISO 字节
将 `0x1040AD00` 与 `0x1014F678` 恢复为原厂 C3.80 逐字节一致，完全解除了对自动 ISO 功能的任何干扰。
