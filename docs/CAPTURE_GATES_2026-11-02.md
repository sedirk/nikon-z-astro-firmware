# 拍摄检查逆向：从错误码 3 到原厂无卡请求被接受

日期：2026-11-02，北京时间。接续[原厂列表生成器验证](LIST_GENERATOR_2026-11-02.md)。本轮只分析本地初代 Z6 C3.80 和固定 QEMU 源码，没有新增网页调研。

## 能否通过逆向避免盲目的黑箱测试

可以，而且本轮就是先读固件，再用模拟器验证具体分支。反汇编用于恢复调用关系、请求布局、掩码和返回条件；断点用于确认实际输入、走过的分支和状态变化。这样能把“为什么没拍照”缩小到某个检查，而不是不断改设置碰运气。

本轮已纠正一个误判：此前持续存在的 0x24 标志，在当前环境中没有参与最终禁止判断。进一步找到原厂拍摄 API 的保存目标检查，以及明确标为 `CaptureWithoutCard` 的原厂分支。按该分支恢复参数后，API 从返回 3 变成返回 0，拍摄服务状态进入 3。

这只是请求被接受和内部状态推进。**尚未确认静态曝光完成、生成 NEF、保留暗电流或关闭任何实际 RAW 像素处理。** 固件之外的传感器、EX MCU 和 ISP 硬件行为仍需模型或真机证据；静态逆向不能完全代替验证。

## 证据范围

- 主程序 SHA-256：`1e6348d58750e67372d0a8e363932c57ee9c04d0eb8f62803bcd19812df0d25c`，加载基址 `0x10020000`，下文地址按 Thumb 指令解释。
- 上游源码固定为 `419a1f2a91a1f2d3a0209027c29606475f7fe26f`；QEMU 10.2.4 二进制 SHA-256 为 `9719480046775a5d40e22b6e22d13fa100a415dae1d52f0ff40a8d57764b9d63`。
- 本轮使用上游合成拍摄/取景启动：人工传感器版本、固定姿态、无镜头回复、TG/ISP 测试路径、默认标定、空表设置 0x29e、禁用尚未模拟的 MVD 调度等。存在明确记录的 RAM 和设备辅助，不是未经辅助的真机启动。
- 本轮没有改固件文件、拦截拍摄函数返回值或直接清除禁止项。AF 消费者实验使用人工通知；其他实验保持原有 AF 通知状态。全部实验结束后关闭模拟器，没有接触真机。
- 断点在诊断调用窗口内观察，部分地址每个调用只记录一次。没有命中不能证明该函数在整个会话中从未运行。`ok=true` 仅表示诊断完成。

## 0x24 来自 AF 通知，但当前不构成有效禁止项

静态关系：AF 服务初始化 `0x100a1de0` 使用队列名 `AfSvQue`；释放服务在 `0x10061ef2` 附近通过 `0x100a1ea0` 注册回调 `0x10061673`（Thumb 位已置位）。通知 `0x04260011` 进入实际代码 `0x10061672`，从报告提取首字节及 `+0xb4` 字段，排队交给 `0x1006157e`。

在该消费者内，状态 0/1 会调用 `0x1006017c(0x24)` 置位，状态 2 会调用 `0x10060122(0x24)` 清除。本轮依次投递 1、2、恢复基线 0，观察到原始位集合分别为 `[0x24]`、`[]`、`[0x24]`。这验证了消费者分支，不证明真实自动对焦工作，也不把状态 2 擅自命名为“合焦”。生产者缓存没有跟着人工修改。

关键在于固件还维护了参与掩码：

| 描述符 | 数据地址 | 当前含义/结果 |
| --- | --- | --- |
| `0xc18b8ac0` | `0xc2376d60` | 原始置位集合，只有 0x24 |
| `0xc18b8ac8` | `0xc2376d70` | 参与掩码，0x24 不参与 |
| `0xc18b8ad0` | `0xc2376d80` | 另一类汇总使用的掩码；当前与原始集合无交集 |

三个描述符均声明 97 位。`0x1005fd20` 判断两个位集合是否相交；`0x1005fec4` 附近的汇总代码以原始集合和参与掩码的交集为依据。当前交集为空，原厂 getter `0x100601d8()` 返回 1，`0x100600bc()` 返回 0。

`release_inhibit_submask=0xc` 也不是第二个独立阻点：`0x10060280` 添加子掩码、首次非零时排除 0x24 的参与位；`0x1006026a` 清除子掩码，归零后才恢复其参与。因此旧记录中的 `active_inhibit_ids` 不能直接翻译成“实际阻止拍摄的原因”。

## 按键位值正确，但按键到拍摄 API 的完整链条尚未恢复

固件键名记录为 40 字节：名称占 32 字节，`+32` 为待定字段，`+36` 为按键掩码。`ID_SW0_RELEASE_HALF` 对应 `0x80000000`，`ID_SW0_RELEASE_ON` 对应 `0x40000000`，与上游输入一致。

半按、全按、回到半按、全部释放使用 `80000000 → c0000000 → 80000000 → 0`。先前诊断没有确认完成曝光。以下原厂 API 实验是独立入口，不代表物理按键到照片输出已经贯通。

## 默认请求为何返回 3

从原厂包装函数 `0x10524bc0` 恢复出拍摄接口 `0x101eedb4(request, callback)`。本轮使用一个 20 字节有效请求，附加 12 字节零填充作为诊断暂存区：

| 请求偏移 | 本轮输入 |
| --- | --- |
| `+0..+3` | 默认全零；无卡分支只将 `+2` 改为 1 |
| `+4/+8/+0xc` | 三个 32 位零值；具体业务枚举未完全命名 |
| `+0x10` | 32 位帧数 1 |

回调为包装函数使用的 `0x10524b7f`。前面的忙状态、释放状态、上下文等检查读到 0，参与掩码检查返回允许的 1。默认请求在 `0x101eefc6` 调用 `0x101ede2e` 检查保存目标，然后收到 3，未进入后续准备函数。

实际执行的默认分支经过 `0x101ede82 → 0x101492a0 → 0x1006fa38` 构造目标信息，再经 `0x10321296 → 0x10255990 → 0x1031fa16` 汇总状态。在 `0x101edefe` 断点读到 `r0=0x00010008`；前面的移位/条件分支检测 bit 16，随后将返回值置为 3。调用者把这个错误向外返回。这是确定的条件拒绝，不是“程序没响应”。

bit 16 的业务枚举名尚未完全确认，因此目前写作“保存目标检查拒绝”，不把它直接等同于“未插卡”。两个默认 API 会话都返回 3；细化观察的第二个会话确认了上述具体位值。

## 原厂 CaptureWithoutCard 分支使请求被接受

包装层字符串包含 `Capture` 和 `CaptureWithoutCard`；其输入 `+8==1` 分支调用 `0x101efaa8(1)`，并把传给拍摄接口的请求 `byte+2` 置为 1。本轮按这一原厂顺序调用，没有替换检查结果。包装层另有用于完成通知的状态字段；本实验直接调用底层 API，未完整执行包装层状态维护，不能声称整个上层命令流程已验证。

结果如下：

| 观察项 | 默认请求 | 原厂无卡参数 |
| --- | --- | --- |
| 请求前 20 字节 | `0000000000000000000000000000000001000000` | `0000010000000000000000000000000001000000` |
| 保存目标检查结果 | 3 | 0 |
| 准备函数 `0x101ee13a` | 未在该调用窗口命中返回点 | 返回 0 |
| 拍摄 API 返回值 | 3 | 0（包装层按接受处理） |
| 拍摄服务 `0xc18b84e0+8` | 基线为 0 | 返回后为 3，后续快照仍为 3 |
| 有效禁止项 | 基线为空 | 快照为 0x27、0x2d |

静态代码也解释了区别：请求 `byte+2=1` 使目标检查跳转至 `0x101edecc`，走原厂允许该目标类型的分支，跳过默认目标状态位检查。不能据此推断无卡路径会生成或保存 NEF。

状态字段的写入接口为 `0x101efbf8`，其 `0x101efc04` 向 `c18b84e0+8` 写字节。本轮 API 接受后，使用原厂等待接口分别传入 100、1000，再读取快照，字段均为 3。上游应用诊断的 `c181a00c.stage` 仍为 0，它是另一个结构，不能与拍摄服务状态混用。

观察到的 0x27 设置来自 `0x10200cfa` 内的 `0x10200d10 → 0x1006017c`。0x27、0x2d 可能与进行中状态有关，目前不命名为故障，也不强行清除。观测窗口内仍选择列表第 6 组、请求 `+0x0c=3`；尚无证据说明已经切换到完整静态 RAW 路径。

## 继续研究的顺序

同日后续：[状态与图像请求追踪](CAPTURE_STATE_2026-11-02.md)已确认状态 3 的计数触发来源，定位到图像请求的等待位 0x100；下列第 1 项以新记录的具体通知路径为继续入口。

1. 以 `0x101efbf8` 的调用者为入口，恢复拍摄服务状态 3 的入口、退出事件和依赖条件；结合 0x27/0x2d 设置者定位需要模型提供的具体消息。只为明确假设增加断点，不批量猜参数。
2. 继续追踪 ID 0x31/0x0c 的源数据和静态照片消费者，确认稀疏位置列表的物理含义。不要把坏点候选列表直接当成彩圈校正。
3. 单独追踪空间颜色增益、黑电平减法/裁切以及邻域过滤。建立“配置或标定数据 → 参数 → 运算或硬件寄存器 → 静态 RAW 缓冲”的证据链，再设计单项修改。
4. 软件分支可用原厂函数隔离执行交叉验证；尚未模拟的硬件像素运算需补模型或用真机暗场、平场验证。保留暗电流和消除彩圈应分别验收。
