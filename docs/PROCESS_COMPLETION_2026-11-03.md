# 图像收尾等待：定位到模拟器未计时的定时器模式

日期：2026-11-03，北京时间。接续[原厂结束通知与后续请求](SOURCE_TRIGGER_2026-11-03.md)。本轮使用本地初代 Z6 C3.80、固定 QEMU `419a1f2`；没有新增网络资料或改写固件、QEMU 设备模型。

## 结论与范围

**发现一个具体的模型缺口：原厂收尾代码配置 8 号定时器时选择了时钟值 0，而当前 QEMU 只为时钟值 `0x31` 计数。** 已记录配置、启动接口返回和回调登记，未观察到回调执行；模型日志只记录了该通道的预置值，没有计时启动或到期记录。这个缺口可以解释所观察到的定时回调缺失，但是否足以解除整条拍摄流程的等待，还需模型对照实验。

当前拍摄序列仍在阶段 `0x800`、等待位 `0x200`，图像控制状态为 6。后续请求的帧对象已进入下层队列，上游三处同步等待均成功返回，设备收尾请求也已执行。

因此可以排除本次环境中的“请求没有送达队列”和“这三处等待失败”两个假设。还不能把剩余问题定性为某个缺失的 ISP 中断，也没有理由强行清除等待位。

这些结论是合成环境里的控制流程证据。没有有效 RAW/NEF 输出、暗电流统计或彩圈改善结果；尚无可刷天文补丁。

## 已实际送入 FRONTEND 的帧

`0x10076a08` 的尾部在 `0x10076cec` 向队列 `0xc2528d40` 追加帧指针。提交值与此前 40 字节参数的首个指针一致，追加前后队列计数从 0 变为 1。随后原厂代码将 `0xc18d1db0+0x1c` 置为 `0x1f`。

较长且正常结束的诊断最终仍为队列计数 1、该字段 `0x1f`。对象注册名称 `FRONTEND`、工作入口 `0x1007410d` 与动态快照一致。这里的 `0x1f` 是下层跟踪掩码，和拍摄序列的 `0x200` 属于不同结构，不能混为一谈。

静态恢复的 `0x100710ee(mask)` 行为是：

1. 加锁，并从下层掩码中清除传入位。
2. 如果队列为空，返回空指针。
3. 如果掩码仍非零，读取队首帧；如果掩码归零，移除队首帧并返回它。
4. 解锁并返回帧指针。

这意味着“掩码尚有位”不等于完全不能读取队首；不能据此宣称五个位全清才会执行任何后续动作。本轮观察的更直接事实是：该函数入口一次也未命中，掩码也保持 `0x1f`。

| 清除位 | 静态调用位置 | 上游路径 |
| --- | --- | --- |
| 1 或 2 | `0x10072580` | `0x10072430` 接收 `0x041f0002`，按载荷首字节选择 |
| 4 | `0x10071a1a` | `0x100714ba` 接收 `0x041f0005` |
| 8 | `0x10072c74` | FRONTEND 工作标志 `0x40000` 对应分支 |
| `0x10` | `0x10076d80` | `0x10143414` 的上层调用 |

这些位尚未逐个命名为真实硬件处理单元，更不是五个 RAW 矫正开关。

## `0x200` 的收尾通知从哪里来

将上次已知的通知末端继续向前连接，得到以下静态路径：

```text
CAPSEQ 工作标志 0x20
  → 0x101e0fbc → 0x101e109c：0x041f0005
  → 0x100714ba → 0x10071a18：取帧，构造 40 字节载荷
  → 0x10071c44：通过下层 +0x48 回调发出 0x04190005
  → 0x101474ae → 0x10147732：登记状态，排队 40 字节
  → 0x10146e60：工作消息前 8 字节为队列头，后接载荷
  → 0x101471b2 → 0x1014a36a → 0x1014a566
  → 若返回 0：0x10141f78 → 0x0415000e
  → 0x101fdaca：解除拍摄序列等待位 0x200
```

该链有真实分支条件。例如 `0x10146e60` 检查载荷中的帧指针；`0x1014a566` 根据请求类别、次数、帧字段和配置决定返回 0、1 或 2。不能把末端发送函数当作无条件成功出口。

当前帧配置 `+0x252` 为 0。按该函数代码，在此次请求类别 0 下，这个值会使它选择返回 0；这是对保存字段的静态条件分析，函数本身尚未在本次正常拍摄链中运行到。该字段的产品含义未确认，不能据此宣称找到了降噪开关。

同一字面常量 `0x041f0005` 在 `0x101e10e0` 还被加载后减 3，实际发送 `0x041f0002`，并使用另一回调槽。原字节、算术和实际回调均要核对，不能只搜索事件常量就合并两条链。

## 上游三处等待都成功了

动态记录到 CAPSEQ 工作标志 4，随后 `0x101e42d2 → 0x100f6786` 向 CAPTG 工作对象提交 `0x100`；之后 CAPSEQ 收到标志 8。当前 `0x101e41b0` 策略检查返回 0，选择普通路径 `0x101e167a`。扩展请求 `0xc236d378` 的字节 `+0xec=1`、`+0xb6=0`、`+0xb7=0`；第二项条件要求 `+0xb6==1`，因此该策略返回 0。

| 调用地址 | 同步对象 | 等待位 | 期限参数 | 原厂包装函数返回 |
| --- | --- | --- | --- | --- |
| `0x101e16c2` | `0xc236d284` | 8 | 3000 | 1 |
| `0x101e16d0` | `0xc236d284` | 1 | 3000 | 1 |
| `0x101e16de` | `0xc236d290` | 1 | 3000 | 1 |

`0x1017115a` 在底层 OS 等待返回 0 时转换为 1，失败分支则转换为 0。因此这里确实执行了成功返回，不能称为超时后继续。没有修改返回值，也没有人为发送对应完成通知。

随后命中 `0x101e1874 → 0x100f6804`。在较长的正常结束诊断中，记录到 `0x100f68d8 → 0x10193194`，以及 `0x100f68dc` 读到返回值 0。源控制状态最后为 5；CAPTG 自身状态字节最后为 `0x0f`。它们均不是拍摄服务的状态值，返回 0 也不能替代最终曝光完成。

另一个入口 `0x101e1990` 虽然命中，但其策略检查返回 0，在提交命令前退出；未观察到 `0x104294ae/0x104294dc` 被调用。普通路径中的额外定时等待点 `0x101e184c` 也未命中。本轮没有改写这些选择条件。

## 新定位：8 号定时器使用当前模型未支持的时钟

最后一次 `timer-probe` 正常结束，记录到以下链条：

```text
0x10193194：两次内部操作均返回 0
  → 0x101931fa → 0x10190ebc(0xc18b7938, ..., delay=0)
  → 0x10190f82 → 0x1010ecae(timer_id=8, config=0xc18b793c)
  → 配置返回 0；0x1010efd4 启动接口返回 0
  → 对象 +0x34 登记回调 0x10193181，+0x30 保持 1
  → 未观察到 0x10193180 回调
```

配置调用前保存的结构字段：

| 相对对象 `0xc18b7938` | 值 | 与原厂驱动的关系 |
| --- | --- | --- |
| +0 | 8 | 定时器编号 |
| +4 | 1 | `0x1010ecae` 使用自定义配置分支 |
| +8 | 0 | 驱动走终值减 1 的分支 |
| +0xc | 0 | 驱动提交的时钟选择字节 |
| +0x10 | `0xffffffff` | 终值参数，驱动写出前减 1 |
| +0x14 | `0xfffffffe` | 预置计数值 |
| +0x34 | `0x10193181` | 原厂回调，含 Thumb 位 |

`0x1010ecae` 在 `0x1010ecf8` 读取配置指针 `+8`，即对象 `+0xc`，传给 `0x1005b3ba`；后者 `0x1005b3da..0x1005b3de` 写出时钟选择值。这里的 0 来自保存参数与原始指令的共同核对，不是把定时器编号 8 当成时钟值。

固定版本 QEMU 计数器实现（`work/src/z6-qemu-419a1f2a91a1f2d3a0209027c29606475f7fe26f/qemu/nikon-z6.c`，本地归档未公开） 的 `nikon_channel_access` 只有在 `channel_config[ch][1][1] == 0x31` 时，才置 `channel_clocked` 并安排到期。源码注释也明确其他选择值不计时。此次日志（`analysis/process-completion-2026-11-03/timer-probe/session/qemu-1.log`，本地归档未公开）第 83066 行记录 `Z6_CHANNEL_PRESET channel=8 value=0xfffffffe`，全文没有该通道的 `Z6_COUNTER_START` 或 `Z6_COUNTER_TERMINAL`。

这是比“可能缺少某个完成中断”更具体的定位。不过，本轮没有读取该次完整 MMIO 配置寄存器快照；时钟值的写入关系由参数快照、原厂驱动和固定模型源码连接。模型缺口已确认，补齐它是否能让 `0x041f0005`、`0x0415000e` 出现尚未验证，不能宣称它是唯一原因。

源码中的 1 微秒计时是假设且仅针对 `0x31`；不能直接把选择值 0 也按相同速率计数。下一步需核对固件的比例换算和时钟配置表，再做限定模式的计数器实验，检查预置、终值、启动、停止和 IRQ/回调顺序。即便解除控制等待，也仍不代表 RAW 像素已经正确产生。

## 诊断记录与失败保留

- `process-probe`：等待参数 10000，176 个事件，正常结束；证实帧入队和下层掩码保持 `0x1f`。
- `readout-probe`：等待参数 30000，196 个事件；已记录三处等待成功及收尾调用，之后宿主 RSP 接收触发 45 秒超时。该次没有 `after_settle` 或最终快照，不能把较早的 `after_api` 快照当作最终状态，也不能将连接超时认定为固件错误。
- `readout-complete-probe`：同样的等待参数 30000，将宿主 RSP 超时改为 180 秒，193 个事件，正常结束；最终仍在 `0x200`，CAPTG 为 `0x0f`。
- `timer-probe`：等待参数 30000、宿主超时 180 秒，204 个事件，正常结束；进一步记录定时器编号、时钟选择值、启动返回和未执行的回调。四次诊断中三次完整结束、一次宿主接收超时；原始失败目录完整保留。

等待参数没有做时间单位校准。断点集合、SMP 调度及宿主运行速度不同，事件数量和用时不能用于相机性能对比。高频回调部分采用每次诊断调用只观察一次；专用分支和通知消费者另有观察点。有限窗口未命中不等于永久不会执行。

模拟器继续沿用上游的人工启动、无镜头、校准数据、取景与 EX MCU 完成线等辅助。日志中存在图像处理输出，仍主要是此前的合成取景路径，不能拿来验收静态照片 RAW。列表选择观察点命中的 mode=3、第 6 组也不能证明后续没有其他模式。
