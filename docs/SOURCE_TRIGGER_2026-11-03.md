# 原厂结束通知已运行，等待推进到后续图像请求

日期：2026-11-03，北京时间。接续[图像等待的上游事件](IMAGE_COMPLETION_2026-11-02.md)。使用本地 Z6 C3.80、固定 QEMU `419a1f2`，本轮没有新增网络资料。

## 本轮推进

**此前的等待位 `0x100` 已由原厂通知链自然解除。** 在更长观察窗口中，实际记录到：

```text
上游工作标志 0x1：启动
  → 设备请求及等待返回
  → 定时回调发出工作标志 0x100
  → 内部阶段 0、1
  → 工作标志 0x2

```

最后等待参数为 5000 的两次独立启动，以及参数为 10000 的一次启动，都记录了这次推进。没有手工发送上述通知、修改返回值或直接写等待位。

这也修正了后续工作的重点：上一轮“未出现结束通知”只适用于当时的短观察窗口，不能作为必须新增硬件完成事件模型的依据。当前应追踪新的 `0x0415000e` 通知。拍摄服务仍处于状态 3，尚未完成整条拍摄流程；没有验证有效 RAW 像素、暗电流保留或彩圈处理改变。

## 启动和结束标志的实际来源

上游工作对象 `0xc236d250` 的内存名称为 `CAPSEQ`，`+0x2c` 登记工作函数 `0x101e26f1`，`+0x30` 为接收掩码 `0x364fffff`。注册代码和动态快照一致。`0x10170cec` 等待标志后调用该函数，`0x10170d38` 向对象 `+0x20` 的事件组提交标志。

短窗口诊断已记录工作标志 `0x1` 和启动函数 `0x101e212e`，排除了“上游没有启动”。随后增加观察点并延长等待，记录到：

1. `0x101dfd06` 提交设备请求，`0x101dfd42` 读到返回值 1。
2. `0x101dfd54` 调用等待接口，r0=`0xc236d284`、r1=`4`、r3=`3000`；`0x101dfd58` 读到返回值 **1**。按原厂包装函数 `0x1017115a` 的返回约定，这是等待成功分支，不是该接口的超时失败分支。
3. `0x101e20d0` 安排后续定时动作；回调 `0x101e0e92` 把阶段字段 `0xc18b7228+0xc` 置 0，提交标志 `0x100`。
4. 工作函数在 `0x101e289c` 根据阶段分派。实际先进入阶段 0 的 `0x101e414c`，随后进入阶段 1 的 `0x101e40ca`。
5. 阶段 1 路径在 `0x101e4126` 前已装配 r1=`2`；之后工作函数实际收到 `0x2`，执行 `0x101e2012`。

三个较长窗口中的上述顺序一致。内部阶段、工作标志和拍摄序列等待位属于不同对象，虽然都有 `0x100`，不能混用。

等待参数保留原数值。本轮没有校准各接口的时间单位或测量真实曝光时长；新增断点也会影响调度。因此这里证明的是“在较长窗口中可以运行过去”，不是精确的时间阈值测量，也不声称观察时长是所有差异的唯一原因。

`source_start_return` 观察点位于一个共用返回尾部，日志中也可被其他路径命中；不能仅凭该标签判断启动函数返回。本轮使用设备返回点、定时回调和完整通知顺序作为证据。

## 新等待位 `0x200` 对应什么

原厂阶段函数在原有等待清零后，调用：

```text
0x10200aea → 0x101484d0(8 字节参数, 0x101fe4c1)
  → 排队至 0x10144b42
  → 登记回调槽 0x0e
  → 0x1013e18a(4)：图像状态 5→6
  → 0x10144c56：检查图像服务 +0x44
  → 0x101424d2
  → 0x10076a08(40 字节参数)
```

next-stage-probe 和 extended-probe 完整比较了提交的 8 字节与工作消息 `+8..+15`，逐字节相同，本次均为 0。API 返回 0。工作函数实际执行，检查时 `0xc18b7dc0+0x44` 为 1，进入 `0x101424d2`；40 字节参数中的首个指针与本次帧对象一致，`0x10076a08` 返回到 `0x101426de`，读到 r0=0。

这些结构是控制参数，不是 RAW 像素。40 字节参数的其他字段尚未逐项命名。下层入口的静态尾部包含帧对象入队、`0x1007240a` 和 `0x101e310e`；本轮没有为每个内部调用分别设断点，不能把其所有分支都视为已经动态验证。

最终序列结构 `0xc2376050`：

| 偏移 | 值 | 解释 |
| --- | --- | --- |
| +8 | `0x800` | 当前序列阶段 |
| +0xc | `0x1020072f` | 当前工作函数，含 Thumb 位 |
| +0x10 | 4 | 等待返回状态 |
| +0x14 | `0x200` | 仍未解除的等待位 |

实际命中 `0x10200742`，返回掩码 `0x200`。回调表 `0xc2375b74+0x0e×4` 仍登记 `0x101fe4c1`。这与前一阶段的 `0x100` 已清除不矛盾；流程已经前进。

## 新通知的静态发送与消费路径

事件 `0x0415000e` 经 `0x101fe53c` 的 TBB 表索引 1，跳到 `0x101fe71c → 0x101fe77a`，排队 12 字节参数给 `0x101fdaca`。消费者在当前序列类别为 1 时，复制该结构，并用 r2=`0x200` 调用 `0x101fc2a2`。

静态发送候选已经找到：`0x10141f78` 构造 12 字节通知，末尾 `0x10141ffa..0x1014200a` 取出槽 0x0e 并发出事件。它的上游 `0x1014a36a` 根据 `0x1014a566` 的结果选择收尾方式；返回 0 时调用 `0x10141f78`。发送函数内部还会检查资源、等待另一事件对象，并使用图像状态字节构造通知，不能把它当作无条件成功出口。

extended-probe 已观察该函数入口、内部等待和发送位置，最后等待参数为 10000 时均未命中。三个较长窗口中都没有收到 `0x0415000e` 或运行其消费者。**这仍然是有限观察结论，不是永久死锁证明。** 下一轮从 `0x1014a36a / 0x1014a566` 的触发条件，以及已经进入的 `0x10076a08` 后续消费者追踪。
